# Идиомы ROS2
## RAII
Идиома гласит - захват (получение) ресурса и есть инициализация. Также освобождение ресурса - это уничтожение объекта.
Самый наглядный пример RAII это выделение памяти хендлеру ресурсов при создании Subsсriber, или Publisher, или Timer неважно
```cpp
SomeNode() : Node("simple_node"){
    publisher_ = this->create_publisher<std_msgs::msg::Bool>("topic", rlccpp::QoS(10));
    //publisher - и есть хендлер ресурсов, при вызове деструктора, publisher автоматически 
    // освободит ресурс который хранит
}
private:
    rclcpp::Publisher::SharedPtr publisher_;
```  

При вызове захвате mutex (примитива синхронизации) освобождение произойдет автоматически при выходи из  области видимости
```cpp
void callback(){
    // блокируем потом
    std::lock_guard<std::mutex> lock(m);
    // проводим действия
    msg.data = "loh"
    //поток автоматически разблокируется, ведь lock_guard освободит ресурсы при выходе из области видимости 
}
```
## Асинхронность и многопоточность
Асинхронность в ROS2 реализована за счет системных вызовов epoll, которые уведомляют executors о наступлении какого-либо события и пробуждают их. Однако сами операции и вычисления накладываются на сами Executors, и тем самым это паттерн Reactor. Стоит уточнить, что использование epoll обеспечивает неблокирующий ввод-вывод на уровне ожидания сообщений, но как только событие наступило, логика внутри соответствующего колбека выполняется последовательно. Если колбек содержит «тяжелые» вычисления, он блокирует поток Executor на время своего выполнения, что может привести к задержкам в обработке других срочных сообщений, поступивших в это же время. 

Многопоточность реализована за счет callback groups, с помощью которых можно распараллеливать вызов колбеков, если архитектура и логика позволяют это. Также MultiThreadedExecutors поддерживают многопоточность. Механизм взаимодействия здесь следующий: MultiThreadedExecutor создает пул потоков, и каждый поток может «занять» только одну CallbackGroup за раз. Это означает, что колбеки внутри одной группы никогда не выполняются параллельно, что автоматически предотвращает состояние гонки (race condition) при доступе к общим переменным этой группы. В то же время, колбеки из разных групп могут исполняться одновременно, что позволяет эффективно нагружать многоядерные процессоры, не прибегая к сложному ручному управлению мьютексами.

## Паттерны проектирования фреймворка
### Interface, Facade
В ROS2 паттерн Interface обеспечивает фундаментальную развязку компонентов и переносимость кода. Он реализуется через абстрактные классы и API RMW (ROS Middleware Interface). Это позволяет пользовательскому коду взаимодействовать с ядром системы через стандартные контракты (например, методы publish() или spin()), не завися от того, какая конкретная реализация промежуточного ПО (DDS) используется (FastDDS, CycloneDDS и др.). Интерфейсы гарантируют, что логика приложения не потребует изменений при смене транспорта связи. 
Например, также реализован класс Node. По факту, он реализует интерфейсы BaseNodeInterface, NodeTopicsInterface, NodeTimersInterface и другие, что позволяет скрыть от пользователя детали реализации.

Facade (Фасад). Паттерн реализуется в клиентских библиотеках, таких как rclcpp или rclpy. Они предоставляют простой, высокоуровневый API, который скрывает за собой колоссальную сложность внутренней архитектуры: работу с сокетами, процессы сериализации, управление памятью и детали протокола DDS. Разработчику достаточно вызвать простой метод создания узла или подписчика, а фасад лишь вызывает сложные низкоуровневые операции инициализации и настройки, делая код чистым и читаемым.

### PIMPL
Паттерн PIMPL или указатель на реализацию в ROS2 применяется для строгого разделения интерфейса и деталей кода, что существенно ускоряет компиляцию и обеспечивает бинарную совместимость библиотек. Суть подхода заключается в том, что в открытом заголовочном файле класса объявляется только указатель на неполный тип реализации, назовем его pimpl, в то время как сами поля, методы и тяжелые зависимости спрятаны в исходном cpp файле. Например, публичный класс rclcpp::Node в заголовке содержит лишь строку NodeImpl* impl_, а все детали работы с DDS и сериализацией лежат в файле реализации, где определяется структура NodeImpl. Благодаря этому при подключении заголовков ROS2 компилятору не нужно обрабатывать каскады внутренних зависимостей, а разработчики фреймворка могут менять внутреннюю кухню классов без риска сломать скомпилированные у пользователя программы.

### State machine
Поведенческий паттерн, который позволяет сторого определять состояния объектов в определенные момоенты времени. Также паттерн должен гарантировать как правильность запуска, так и определенность при завершении работы.
Главный пример rclcpp::LyfeCycleNode. Смотри lesson_fifth.cpp

### Fabric
Узел или метод выступает фабрикой для своих компонентов. 
Создание узлов, паблишеров, сабскрайберов и таймеров и есть реализация фабричных методов. Они не создаются их через new Publisher(), а через фабричные методы у ноды: node->create_publisher<MsgType>("topic", qos);

### Builder
Порождающий паттерн, который в момент множетсва параметров класса вместо перегрузки конструктора создает цепочку вызовов.
Самый понятный пример - rclcpp::QoS
```cpp
Qos() {}
&QoS QoS::history() {}
&QoS QoS::durability() {}
//и тд.
// то есть методы класса просто добавляют параметры qos в класс и возвращают ссылку на новый экзепляр
// вместо перегрузки конкструктора множествами этих методов
``` 

### Singleton
Порождающий паттерн, цель которого обеспечить единый интерфейс внутри себя, не разбивая его на другие классы. и при этом являться единственным классом с определенными функциями.
Когда вы вызываете rclcpp::init(), под капотом создается глобальный контекст (внутри используется std::weak_ptr и механизм инициализации), который является единым для всех нод в данном процессе. Он хранит глобальное состояние DDS middleware, общиеinterrupt-обработчики и т.д. Нельзя случайно создать два независимых контекста в одном вызове.


# C++ глоссарий
### Mutex
Мьютекс - примитив сихнронизации, который гарантирует, что в каждый момент времени поток, который захватил мьютекс, будет исполняться пока другие потоки будут ждать
Примеры с дефолтным std::mutex
```cpp
std::mutex m;
{
std::lock_guard<std::mutex> lock(m);
// что то делаем
}
// вот тут мьютекс освободит поток согласно идиоме RAII

//Вот так делать нельзя, ведь возникнет взаимная блокировка (deadlock)
std::mutex m1;
void f(){
    std::lock_guard<std::mutex> lock(m1);
}
int main(){
    std::lock_guard<std::mutex> lock(m);
    f();
}
```

Есть еще std::timed_mutex - у которого можно задать дедлайн разблокировки потока и освобожднии ресурсов
В ROS2 чаще вижу std::recursive_mutex. Ведь он позволяет одному и тому же потоку захватывать мьютекс несколько раз. Это полезно, если функция, блокирующая данные, вызывает другую функцию, которая тоже пытается их заблокировать. 
```cpp
//А вот благодаря recursive_mutex так можно. Особенно в ROS2 при wait_set паттерне используются
std::recursive_mutex m1;
void f(){
    std::lock_guard<std::recursive_mutex> lock(m1);
}
int main(){
    std::lock_guard<std::recursive_mutex> lock(m);
    f();
}
```
### Guard Condition
В ROS 2 это примитив для уведомления **Executor** о событии из другого потока. Если мьютекс **запрещает** доступ, то Guard Condition **разрешает** (пробуждает) выполнение.

```cpp
// 1. Создание в ноде
auto gc = std::make_shared<rclcpp::GuardCondition>();

// 2. В потоке А (ждем событие)
// Executor автоматически "просыпается", когда gc активирован

// 3. В потоке Б (сообщаем о событии)
gc->trigger(); // Мгновенно будит поток А
```

---

### Сравнение в паре
Обычно они работают вместе: мьютекс защищает общие данные, а Guard Condition сигнализирует об их готовности.

```cpp
std::mutex mtx;
std::vector<int> data;
auto gc = std::make_shared<rclcpp::GuardCondition>();

// Поток записи
void producer() {
    {
        std::lock_guard<std::mutex> lock(mtx);
        data.push_back(42);
    }
    gc->trigger(); // Будим ноду для обработки
}
```
