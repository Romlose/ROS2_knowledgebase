Docker — это технология для упаковки кода и всех его зависимостей в изолированную среду, называемую контейнером. В отличие от виртуальных машин, контейнеры используют ядро хост-системы, что делает их легкими и быстродействующими. Базовая структура Docker состоит из образа - immutable шаблон с файловой системой и настройками, контейнера - запущенный экземпляр образа, Dockerfile текстовый набор инструкций для сборки образа и реестра хранилище для распространения образов.  

Манифест образа (Image Manifest) — это JSON-документ, описывающий содержимое и параметры запуска конкретного образа. Он содержит уникальные идентификаторы и дайджесты хэши слоев файловой системы, из которых собирается образ, а также указывает на конфигурацию команды запуска, переменные окружения, порты. В случае мультиархитектурной сборки используется список манифестов Manifest List, который выступает как указатель, направляющий Docker-демон к нужному манифесту в зависимости от архитектуры процессора целевой машины, например, отдавая версию для x86 на сервере и версию для ARM на борту робота. 

В создании робота Docker применяется на трех ключевых этапах. На этапе разработки он решает проблему несовпадения окружений, позволяя всей команде работать в одинаковой изолированной среде с нужными версиями драйверов, библиотек и промежуточного ПО вроде ROS, независимо от операционной системы ноутбука разработчика. На этапе тестирования и симуляции Docker используется для запуска физических движков и алгоритмов в чистых контейнерах, что обеспечивает воспроизводимость результатов и предотвращает конфликты зависимостей симулятора с другими проектами на машине. На этапе развертывания на реальном железе Docker гарантирует, что протестированный код запустится на встроенном компьютере робота точно так же, как на стенде разработчика, так как в контейнер упакована вся необходимая runtime-среда, что критично важно для работы с разнообразными и часто ресурсоограниченными одноплатниками. 


# Lesson 1
Подробнее про контейнер (нагенерил): 
Контейнер — это изолированная среда выполнения, в которой запускается приложение вместе со всеми необходимыми зависимостями, библиотеками и конфигурациями. Контейнер использует общее ядро операционной системы хоста, но при этом обеспечивает разделение процессов, файловой системы, сетевых интерфейсов и других ресурсов, что позволяет запускать несколько контейнеров независимо друг от друга на одной машине. Каждый контейнер создаётся на основе образа, который содержит файловую систему, необходимые бинарные файлы, библиотеки, переменные окружения и инструкции запуска. Контейнеры обеспечивают воспроизводимость среды, упрощают развертывание и масштабирование приложений, а также позволяют эффективно использовать ресурсы системы за счёт минимального оверхеда по сравнению с виртуальными машинами. Управление жизненным циклом контейнера (создание, запуск, остановка, удаление) осуществляется с помощью инструментов контейнеризации, таких как Docker. Контейнеры широко применяются для стандартизации среды разработки, тестирования и эксплуатации программного обеспечения, а также для обеспечения безопасности и изоляции приложений. 
И да, Docker это не единственный инструмент для работы с контейнерами. Шортсы говорили про какие то решения, которые все чаще заменяют докер благодаря легковесности по сранению с этим мамонтом разработки. Например Podman

В данном уроке за основной образ мы возьмем ros-base:humble, легковесный базовый образ ros2. Также существуют ros:distro-core - самый легковесный образ, distro-desktop, desktop -full - наиболее полные и расширенные образы для симуляции, визуализации. 

Рассмотрим основные:
FROM image — задаёт базовый образ, на основе которого будет строиться новый образ. Все последующие инструкции будут выполняться относительно этого базового слоя.
ENV key=value — устанавливает переменные окружения, которые будут доступны на всех последующих шагах сборки и в запущенном контейнере.
WORKDIR /path/to/dir/in/container - устанавливает рабочую директорию в образе. Если директории не существует, она будет создана автоматически. Эта директория сохраняется и используется по умолчанию при запуске контейнера. Если WORKDIR не указан, по умолчанию используется корень файловой системы — /.
COPY src dest — копирует файлы или директории из контекста сборки на хосте в файловую систему образа по указанному пути.
RUN command — выполняет указанную команду в процессе сборки образа. Результаты выполнения сохраняются в слое образа.
ENTRYPOINT ["executable", "param1", ...] — определяет основную команду, которая всегда будет выполняться при запуске контейнера. Может использоваться совместно с CMD для передачи аргументов.
EXPOSE port — информирует о том, что контейнер прослушивает указанный порт во время выполнения. Не открывает порт на хосте автоматически.
VOLUME path — объявляет точку монтирования для внешних томов или директорий, обеспечивая сохранение данных вне контейнера.
USER username|UID — задаёт пользователя, от имени которого будут выполняться последующие инструкции и процессы в контейнере.
ARG name=default — определяет переменную для передачи значений на этапе сборки образа. Доступна только во время сборки.
LABEL key=value — добавляет метаданные к образу в виде пар ключ-значение для идентификации или описания.
CMD ["executable", "param1", ...] — задаёт команду, которая будет выполнена по умолчанию при запуске контейнера, если не указано иное.

Сбор образа осуществляется по слоям, например, есть слой RUN ..., и при изменении его или слоя выше, например ENV = ..., Docker будет пересобирать все, с момента изменения. Поэтому стратегию размещения зависимостей лучше продумать заранее для оптимизации кеширования

Сбор образа:
```bash
#сборка
docker build -t ros2_image .
#запуск, с монтированием директорий для GPU и GUI, если мы не указали явно в Dockerfile
#во втором уроке мы сделаем запуск удобнее без километровых команд
docker run -it --network host --gpus all -v ./src:/ros2_ws/src -v /tmp/.X11-unix:/tmp/.X11-unix ros2_image bash
```

## Entrypoint
Когда мы собираем образ и запускаем контейнер, мы сталкиваемся с одной неприятной особенностью. По умолчанию внутри контейнера не активировано окружение ROS 2. Если мы просто передадим команду запуска ноды, система выдаст ошибку, потому что не знает пути к исполняемым файлам. Чтобы не заставлять пользователя каждый раз вручную прописывать source базового пути и пути рабочего пространства, используется скрипт точки входа. Этот скрипт автоматически подхватывает переменные из Dockerfile, загружает базовое окружение ROS, а затем проверяет, собрано ли наше рабочее пространство, и если да, тоже загружает его. После этих подготовительных шагов скрипт передает управление той команде, которую мы указали при старте. Здесь применяется специальная конструкция exec, которая заменяет процесс скрипта на целевую команду. Это нужно для того, чтобы контейнер корректно реагировал на сигналы остановки от операционной системы. Без exec команда docker stop может убить только скрипт, оставив процесс ноды висеть в памяти. Чтобы все это сработало, мы копируем файл скрипта в образ, даем ему права на выполнение и указываем как ENTRYPOINT в Dockerfile.
## Docker-compose
Когда базовый образ с точкой входа готов, управлять запуском удобнее всего через docker-compose. Этот инструмент позволяет не писать длинные команды в терминале с десятками флагов, а описать всю конфигурацию в понятном файле. В этом файле мы задаем переменные окружения для домена и реализации DDS, чтобы они применились при работе контейнера. Затем мы монтируем папку с исходниками с хоста внутрь рабочей директории контейнера. Это позволяет писать код в привычном редакторе на основной машине, а внутри контейнера выполнять сборку и запуск без необходимости пересобирать сам образ Docker. Для работы графических интерфейсов вроде RViz добавляется проброс иксов из временной директории хоста.
Самый критичный блок в этом конфигурационном файле для ROS 2 это настройка сети. Мы жестко указываем режим host, полностью отключая внутреннюю сетевую изоляцию докера. В архитектуре ROS 2 нет центрального сервера, и ноды обнаружывают друг друга через рассылку по протоколу UDP. Обычный проброс портов здесь не сработает, и ноды из разных контейнеров просто не увидят друг друга. Режим хоста решает эту проблему, делая контейнер прямым участником сети машины. В отдельной секции прописывается проброс видеокарты через механизм deploy. Это современный метод передачи драйверов и вычислительных мощностей GPU прямо в изолированную среду, что абсолютно необходимо для любых задач с компьютерным зрением или симуляциями физики. В самом конце конфигурации идет блок command. Поскольку скрипт точки входа уже подготовил всю среду, здесь мы просто пишем нужную команду, будь то запуск интерактивного терминала для отладки или прямая инструкция запустить конкретный узел ROS 2.
Ну и конечно, сборка и запуск становятся гораздно проще:
```bash
docker compose build .
#можно указать конкретный образ
#docker compose build container2

#запуск всех контейнеров (-d container_name для запуска конкретного)
docker compose up
#можно отдельно вывести логи контейнера
docker compose logs
#можно выводить логи в реальном времени
docker compose logs -f
#завершение с полным удалением, иначе у нас остануться висеть контейнеры
#с логами и параметрами запуска. Нужно это для анализа после завершения процесса
docker compose down --remove-orphans
```
